Query Service Account API

A searchable, pageable view over user‑managed service accounts

GET|POST /_security/_query/service_account  ·  cluster:admin/xpack/security/service_account/query

→ ← space or click to move · Home/End · g number ⏎

Why, and what

From "two filters and a scroll" to a query with a page boundary

Before: GET /_security/service/apps

{
  "apps/worker_1": { "type": "user_managed",
                     "roles": ["monitor_role"], "enabled": true },
  "apps/worker_2": { … },
  … every account in the namespace, no total, no page
}
  • Filter only by namespace/service name
  • No total, no from/size, no sort
  • Can't ask “who holds role X?” or “which are disabled?”

After: POST /_security/_query/service_account

{ "query": { "bool": { "filter": [
      { "term": { "roles": "monitor_role" } },
      { "term": { "enabled": true } } ] } },
  "sort": ["username"], "size": 2 }
{ "total": 3, "count": 2,
  "service_accounts": [ {
    "username": "apps/worker_1", "type": "user_managed",
    "roles": ["monitor_role"], "enabled": true,
    "_sort": ["apps/worker_1"]  ← search_after cursor
  }, … ] }

A list, not a map: sorted pages keep their order. Built-ins are Java constants, not documents, so they stay with the get API.

Reaching the documents

The index is shared, so the query is fenced three times

Accounts sit in .security beside users, roles and API keys, and share the field names username, roles, enabled. Unfenced, terms roles:[superuser] matches user documents and exists: api_key_hash becomes a probe.
ServiceAccountBoolQueryBuilder.build(...)
if (queryBuilder != null)
    finalQuery.must(SERVICE_ACCOUNT_FIELD_NAME_TRANSLATORS.translateQueryBuilderFields(queryBuilder, null));  // ①
finalQuery.filter(termQuery("doc_type", SERVICE_ACCOUNT_DOC_TYPE));                                            // ②
// ③ doToQuery / doRewrite: context.setAllowedFields(ServiceAccountBoolQueryBuilder::isIndexFieldNameAllowed)

① Build time · coordinator

Rebuilds the query through the allowlist username, roles, enabled. Rejects other fields, patterns, terms lookup, and whole types it can't walk (regexp, query_string, wrapper, script…).

The guarantee. Runs before any search is sent.

② In the query · every shard

Unconditional doc_type filter as a sibling clause; the caller's whole query is one must inside ours.

Fixes leakage: role+enabled query returns 1, not 2.

③ Lucene time · local only

setAllowedFields makes everything else look unmapped. Writeable name is "bool", so a remote shard sees a plain BoolQueryBuilder.

Belt, not braces — which is why ① refuses what it can't inspect.

The allowlist in practice

QueryResult

  • prefix "apps/" is exact: a stored principal is always ns/svc. No runtime namespace field needed.
  • Allowlist, not denylist: a future field isn't queryable until someone adds a translator.
  • version and doc_type stay out on purpose.

Who may call it

Privileges are action-name globs, so the name is the decision

// one glob, no edit
MANAGE_SERVICE_ACCOUNT_PATTERN =
    Set.of("cluster:admin/xpack/security/service_account/*");

// explicit list, one edit
READ_SECURITY = … Set.of(
    GetServiceAccountAction.NAME,
+   QueryServiceAccountAction.NAME,
    GetServiceAccountCredentialsAction.NAME + "*", …)
Reads live under service_account/, writes under user_managed_service_account/ (manage_security only). Naming the query under the write prefix would make it the one read needing manage_security while get still discloses the same data.

Anything later named under service_account/ inherits manage_service_account. A future write must not go there.
Wire, BWC, availability

Nothing new crosses a node boundary

// QueryServiceAccountRequest / Response
@Override public void writeTo(StreamOutput out) {
    TransportAction.localOnly();
}
// TransportQueryServiceAccountAction extends TransportAction,
// not HandledTransportAction: no wire handler is registered.
  • No TransportVersion: request and response never serialize. Only the ordinary SearchRequest travels.
  • No rolling-upgrade feature check on read (same as get and delete); an old node answers 400 no handler, and clients gate on the capability.

Recap

Five sentences

  1. Shape: a read action under service_account/, a five-field request, a list response with a search_after cursor; built-ins stay with get.
  2. Fences: allowlist at build time, doc_type filter in the query, allowed-fields at Lucene time, because the index and its field names are shared; fence ① is the one that survives the wire.
  3. Privilege: the action name is the decision; one line in read_security, none in manage_service_account; query ≡ get for every privilege.
  4. Wire: local-only, so no TransportVersion; capability gates upgrade and multi-project, where the result is empty like get.
  5. Layers: REST parses, transport fences, service decides availability, store searches; 94 unit + 7 YAML pin it.
